## 4. Verification and signed POST checks

GET requires hub.mode=subscribe, the configured hub.verify_token, and a nonempty hub.challenge. A valid request returns the EXACT challenge as plain text with HTTP 200. Wrong/missing parameters return 403; disabled/missing configuration or nonpersistent queue configuration returns 503.

Placeholder-only curl example (Bash; use curl.exe on Windows). Do NOT replace the placeholder token with a real secret in shell history or process arguments:

~~~sh
curl --get 'https://STAGING_HOST_PLACEHOLDER/webhooks/messenger' \
  --data-urlencode 'hub.mode=subscribe' \
  --data-urlencode 'hub.verify_token=VERIFY_TOKEN_PLACEHOLDER' \
  --data-urlencode 'hub.challenge=000123'
~~~

Use Meta's protected setup form for real verification. This illustrative command rejects unless the server uses that fake placeholder in an isolated test. Do not use curl -v or record URLs containing a real verify token.

POST verifies X-Hub-Signature-256 as sha256=<HMAC hex> over the exact unmodified raw body using the App Secret, with constant-time comparison. Missing/malformed/incorrect signatures return 403 before persistence/dispatch. Malformed payloads return 400; acceptance/queue failures return retryable 503. Valid supported events return EVENT_RECEIVED after durable acceptance, not necessarily after worker completion.

For repeatable fake-secret signed POST, valid creation, wrong token/signature and duplicate-envelope tests, use an isolated development/test checkout with uncached test configuration:

~~~sh
php artisan test --filter=MessengerFoundationTest
~~~

The fixtures configure fake secrets in process and use SQLite memory. Do not paste a real App Secret into a command or replay live bodies through ad hoc shell tools.

## 6. Safe diagnostic commands

Run from the application directory with normal staging operator access:

~~~sh
php artisan route:list --path=webhooks/messenger
php artisan migrate:status
php artisan messenger:readiness
php artisan messenger:readiness --diagnostics
php artisan messenger:readiness --diagnostics --entry=123
~~~

Replace 123 only with an INTERNAL numeric entry ID from the UI/operator record. It is not a token or provider message ID.

The read-only command:
- reports configured/enabled flags without values; unusual queue names are shown as CUSTOM/MISSING;
- reports expected route presence, HTTPS configuration and debug/key flags;
- checks table presence and inbox-user existence;
- reports latest Messenger conversation ID and latest (or selected) Incoming entry IDs;
- reports received/status/provider-ID flags, provider metadata presence, explicit pivot count and count of rows sharing that entry's external_message_id;
- reports event status counts, database queue waiting/reserved counts and failed Messenger job count without bodies, payloads or exceptions;
- catches infrastructure errors without printing SQL/configuration details.

It does not send, enqueue, retry, modify records, test real credentials, or prove worker liveness. Exit zero means the report ran, NOT that deployment is ready. Missing tables/UNAVAILABLE and any NO flag must be investigated. Table presence is not a substitute for completed column/index migrations.

For queue health combine the process-manager status with two diagnostic snapshots around the test: a successful job should finish, the event processed count should increase, and failed counts should not increase. Zero jobs alone does not prove a worker is running.

Use the diagnostic's failed Messenger count rather than dumping failed_jobs payloads/exceptions. Review a specific failed job privately; do not use queue:retry all. A failed dispatch may leave an event pending without a job; an actual Meta redelivery can redispatch it after the queue problem is corrected.

For recent event CODES only, on Linux with the standard single-file log:

~~~sh
grep -oE 'messenger\.[a-z_]+' storage/logs/laravel.log | tail -n 30
~~~

On PowerShell:

~~~powershell
Select-String -LiteralPath storage/logs/laravel.log -Pattern 'messenger\.[a-z_]+' -AllMatches | ForEach-Object { $_.Matches.Value } | Select-Object -Last 30
~~~

Choose the current log file if your deployment uses daily logs. These commands deliberately omit full lines/context. Do not share raw logs, .env, config:show output, tinker model dumps, queue payloads, or exception traces.

### Durable safety, errors and diagnostics

An explicit send request UUID has a database unique constraint; repeated submission returns the same entry, not another row. Each entry has one unique outbound attempt and an opaque correlation UUID. The queue payload contains only its internal entry ID. A row lock claims the attempt and commits `attempting` before HTTP. No DB transaction retry includes HTTP. Successful/uncertain/terminal attempts cannot send again. Only an explicit HTTP 429 Graph error rejection retries, with 30/120/600/1800-second backoff, at most five attempts. Permanent 400/401/403 responses fail without blind retry.

Timeouts, 5xx and malformed successful responses have uncertain acceptance and are marked Failed / acceptance_unknown, without automatic resend. This deliberately favors avoiding duplicate delivery over automatic recovery. A worker interrupted after claiming is also uncertain on reexecution after 30 seconds. No exactly-once guarantee is claimed for a remote API without an established replay key. Do NOT clear attempt state or press Send with a new request to work around unknown acceptance. Check the Page/Tester history and inbound echoes first. Correlated authenticated echoes can recover acceptance even if the HTTP result or local acknowledgement write was lost. Metadata correlation must survive Meta's echo; this must be verified during staging. Unknown/unmatched echoes continue through existing inbound reconciliation.
